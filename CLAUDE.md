# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

AnywhereLLM is a Flutter chat client for Android phones for an AnythingLLM server. It shows workspaces and their chats (AnythingLLM threads), streams answers, and manages each workspace's documents, instructions and answer settings in the workspace's pages. It opens the pages of the agent's apps and browser in a web view, and shows an answer that finished out of sight as an Android notification. It keeps the server address and API key in the Android Keystore and its other preferences in a JSON file. It calls AnythingLLM's own API, and the toolkit's when there is one, directly, over https or over plain http on a private network (below); there is no backend of its own.

## Commands

```bash
flutter pub get
flutter analyze
flutter test                                   # whole suite; fakes the server and the keyring
flutter test test/ui/shell_test.dart           # one file
flutter test --plain-name 'a new server starts afresh'   # one test by name
flutter run -d <android-device>                # a phone over adb, or an emulator
flutter build apk --debug                      # -> build/app/outputs/flutter-apk/app-debug.apk
flutter build apk --release                    # needs android/key.properties
flutter test tool/store_graphics.dart          # store graphics -> build/store/en-US, or $STORE_GRAPHICS
flutter test tool/screens.dart                 # each screen at 390x844, light and dark -> build/screens, or $SCREENS
flutter test tool/app_icon.dart                # icon pictures -> assets/icon, and the notification icon
uv run tool/audit/audit.py                     # walk the app on an emulator over the test fakes, light and dark -> build/audit/*.zip; `--help` lists the options
uv run tool/parity/parity.py --help            # Muse parity test harness: docs/protocols/muse-parity-process.md
uv run tool/e2e/e2e.py --bridge ~/bridge       # the real app against a throwaway AnythingLLM and anywherellm-bridge, from a bridge checkout; `--help` lists the options
```

A release APK is signed with the key named in `android/key.properties` (gitignored), which the personal F-Droid repo's `appstore sync` writes the first time it builds the app. Without that file the release build fails rather than signing with the debug key, because every later update must carry the first release's key. `android.enableResourceOptimizations=false` keeps the launcher icon at the path fdroidserver reads, and `allowBackup` is off so a restored backup never carries a Keystore-encrypted key to a device that cannot decrypt it. Its launcher icon and launch screen are made from `assets/icon`, drawn by `flutter test tool/app_icon.dart` from the robin mark (`RobinMark`, `lib/ui/widgets/robin_mark.dart`) in the Lite prototype's icon colours (`iconGround`, `iconInk`). After changing them, run `dart run flutter_launcher_icons` and `dart run flutter_native_splash:create` (configured in `flutter_launcher_icons.yaml` and `flutter_native_splash.yaml`) and commit the generated resources. It needs the Android SDK; `minSdk` is Flutter's default (24), which is what `flutter_secure_storage` requires.

The F-Droid store page's feature graphic and phone screenshots come from `tool/store_graphics.dart`, which draws them with the app's own fonts over the test fakes, so no real server shows; copy `build/store/en-US` to `metadata/local.anywherellm.lite/en-US` in the app_store project (its `phoneScreenshots` replaced whole, since the store lists every file there, and its `icon.png` kept, since the tool does not draw it), whose `appstore.toml` holds the listing text, and run `appstore sync` there.

## Naming

- The product is **AnywhereLLM Lite**, on `master`. Lite has launcher label `AnywhereLLM Lite` (`android/app/src/main/AndroidManifest.xml`) and application ID `local.anywherellm.lite` (`applicationId` in `android/app/build.gradle.kts`). The Kotlin `namespace` stays `local.anywherellm.anywherellm`, which only names the generated classes. The store builds it from a clone at `~/Dev/Apps/anywherellm_lite` kept on `master`, so that clone's `android/key.properties` holds Lite's own release key. The Dart package is `anywherellm`, so imports are `package:anywherellm/...`. The repository folder is still `everything`.
- `flutter_secure_storage` keys its keyring entry by the application ID. Changing `applicationId` orphans any saved key.

## Architecture

Imports run `ui -> core <- adapters`. `lib/main.dart` is the only file that knows both sides. `test/layers_test.dart` enforces this with substring checks on import targets:

| Layer | May not import |
| --- | --- |
| `lib/core` | Flutter, `dart:io`, `dart:ui`, `http`, `flutter_secure_storage`, `file_picker`, `mobile_scanner`, `webview_flutter`, `ui`, `adapters` |
| `lib/adapters` | Flutter, `dart:ui`, `file_picker`, `mobile_scanner`, `webview_flutter`, `ui` |
| `lib/ui` | `dart:io`, `http`, `flutter_secure_storage`, `adapters` |

**Core** holds the ports (`core/ports.dart`: `AnythingLlmApi`, `SettingsStore`, `PrefsStore`, `ToolkitApi`), the server models (`core/server_models.dart`: `Workspace`, `Thread`, `ChatMessage`, `Citation`, `WorkspaceDoc`, `DocEntry`, `DocBody`, `SearchHit`), and the pure logic, one file per concern: `chat.dart` (events, modes, titles, attachments, `openableLink`, `loadableImage`, status lines, `modelFailure`, `refusesPictures`, `splitReasoning`), `files.dart`, `json.dart`, `outputs.dart` (generated files, answer metrics), `system_settings.dart`, `providers.dart` (`Provider`, a chooser's value with its name and, for a chat provider reached at an address, the setting that holds it; the choosers; the lines Privacy and data shows), `chat_groups.dart`, `sources.dart`, `prefs.dart`, `find.dart`, `markdown.dart`, `gallery.dart`, `upload.dart`, `connection.dart` (`keySafe`, `isPrivateHost`, `Pairing`, `parsePairingCode`, and `isLoopback`, which `chatModelPrivacy` reads as the server's own machine, with `host.docker.internal` besides), `schedule.dart`, `schedule_spec.dart` (when a task runs as a person writes it, in local time, and the UTC cron it becomes), `activity.dart`, `memory.dart` (with its limits), `copy.dart`, `companion.dart` (`Companion`: what a server beside AnythingLLM shares: its own address, the developer key and a `/health` naming its `service`; `segmentsOf` and `under` reach one behind a path prefix), `toolkit.dart`, `skill_pages.dart`, `browser.dart`, `signed_in.dart`, `apps_lean.dart`. Every failure is an `ApiException(message, {status})` (`core/errors.dart`); `NotConfigured` is the subtype thrown when no server is set up, and `CutOff` the one for a streamed answer whose connection dropped or fell silent after the server took the question. To run calls at once, use `Future.wait` on futures that catch their own errors: the record `.wait` wraps errors in `ParallelWaitError`, which breaks the `on ApiException` handlers.

**The connection** lives in one shared `ConnectionHolder`, built in `main.dart`. `HttpAnythingLlmApi` reads it on every call, so a saved connection takes effect without a restart. `SettingsController` is the only writer, through `load`, `save`, `clear` and, after `verify`, `connect` and `pair`, which notify listeners. `ChatController` listens and starts afresh when the connection changes; `SessionHost` builds it before reading the keyring, so reading a saved connection is what loads the workspaces. `verify(Connection)` takes an explicit connection so Settings can test one before saving; `SettingsController.connect` verifies first and saves only on success. A test's answer that arrives after another test began, or after the connection in use changed, is dropped.

**https, or http on a private network.** Dart's `HttpClient` ignores Android's cleartext policy, so the app keeps its own rule (`keySafe`, `isPrivateHost` in `core/connection.dart`): the key goes over https anywhere, and over plain http only to a private host: `localhost`, a name with no dot that is not a number, a name under `.local`, `.lan`, `.home.arpa` or `.ts.net`, an IPv4 address in `127/8`, `0.0.0.0`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16` or Tailscale's `100.64/10` written as four plain decimal parts (a resolver may read `134744072`, `010.0.0.1` or `10.1` as a public address, so none counts), or IPv6 `::1`, `fc00::/7` or `fe80::/10` with the first group written in full (`fd00::1`, not `fd0::1`); an empty host name (`.`) is not private. `normalizeBaseUrl` refuses any other http address (`plainHttpRefused`) and a host name of anything but letters, digits, dots, hyphens and underscores (a name outside ASCII is percent-escaped by `Uri.parse` and no resolver finds it; its `xn--` form is taken). Every call and `verify` check the address again before the key is sent (`_secure`), and the same rule decides an answer's image, a companion's address and an app page in the web view; the manifest's `usesCleartextTraffic` lets Android load such a page. A saved http connection (`Connection.plainHttp`) shows a Plain http warning on the Connection page, and the pairing sheet shows one for each http address a link names (`plainHttpWarning`): the key goes unencrypted to whatever answers that host on the network the phone is on, which on another Wi-Fi, or on mobile data with Tailscale off, can be another machine.

**Scanning a pairing code.** Scan QR code on Settings' Connection page reads a code another AnywhereLLM drew, `anywherellm://connect?url=...&key=...`, with `AppScope.scanner`; the code shows in Connect to this server? (`PairingSheet`, through `ShellController.showShared`) as a tapped link does, since a code on a sticker can name any server, and the sheet says why when `parsePairingCode` refuses it; its Connect hands it to the Connection page (`ShellController.pairWith`), which saves it through `SettingsController.pair`. Nothing of a code is put in the form, which goes back to the saved connection (`_backToSaved`) whether it paired or not, so a key typed after a failed code never goes to the address it named; why it failed shows under the form. The scanner is `cameraScanner` (`ui/settings/scan_code.dart`, `mobile_scanner`), imported by `main.dart` only; tests pass a fake or null, and with none there is no Scan button. The camera shows in `ScanView` (`ui/settings/scan_view.dart`), a page over the window under Back, heard as Cancel, with the camera in a square as wide as the page's content, where to find the code and How connecting works; whether it is open is `ShellController.scanning`, which Esc and Back stop first. `mobile_scanner` bundles Google ML Kit (`libbarhopper_v3.so`, not free software) and adds about 17 MB to the release APK; its manifest adds the CAMERA permission with the camera marked optional.

**Dictation.** The composer has a microphone where there is `AppScope.dictation`. `Dictation` (`ui/chat/dictation.dart`) is the port: `start` gives the words heard so far in full each time and calls `onDone` once when listening ends, with the `DictationEnd` that ended it: `stopped` by `stop`, `paused`, or `failed`. `SpeechDictation` (`ui/chat/speech_dictation.dart`, `speech_to_text`) is imported by `main.dart` only. What is heard follows the message as it stood when listening began. A change to the message made otherwise, by typing, a shortcut or Edit, ends the go and is kept. Sending ends the go, and words that arrive after it are dropped. `done` ends a go, not `notListening`, which comes before the last words. `SpeechDictation` gives each go its own id, and `start` waits for a stop in flight, so the `done` that stop brings never ends the next go. With `ChatSwitch.sendDictation` on, a go that ended `paused` after it heard words sends the message when `canSend` (`ui/chat/composer.dart`) allows it, the same check the Send button makes; a pause that heard nothing, a go the person stopped and one that failed leave the message in the box. The manifest adds `RECORD_AUDIO` with the microphone marked optional and a `queries` entry for `android.speech.RecognitionService`; recognition runs in the device's own service, which may send the audio to its maker.

**The developer key alone.** The app reaches AnythingLLM through its developer API (`/api/v1`) with the developer key, and never signs in to the web UI. What only the web login opens (`validatedRequest`: deleting a thread's exchanges, marking an answer, saved memories, scheduled jobs, AnythingLLM's own web push, developer keys, slash-command presets) the app leaves alone, or reaches through the toolkit when it runs beside the server (Memory and Upcoming). So Retry and Edit leave the old exchange on the server beside the new one, and an answer cannot be rated. `Connection` is the address and the key alone, and `Connection.parse` refuses a key with a character outside printable ASCII (`[\x21-\x7e]`), since an HTTP header refuses it and the refusal's text would quote the header, key included. The toolkit, the anywherellm-bridge, may run beside AnythingLLM (the bridge listens on port 8467 by default; the app uses only the address its pairing link names, `toolkitCompanion`); its `/health` names it `anywherellm-bridge`; its earlier names `anythingllm-bridge` (before the rename) and `anythingllm-toolkit` (before the suite) still count (`Companion.formerly`, `Companion.names`); `ToolkitController` (`ui/state/toolkit_controller.dart`, built in `main.dart` over the `ToolkitApi` and the settings) follows it through `CompanionWatch`: whether it is there and which `ToolkitFeature`s it `serves`, the ones its bridge lets through, asked once a connection and again on Test connection; it also reads the scheduled jobs. Lite works fully without it. While the toolkit serves nothing (`CompanionWatch.servesNothing`: it does not answer, or its bridge passes none of the app's calls, which the card then says), Settings' list ends with a `SummaryCard`, Get more from your server, whose See how to add it opens Add the toolkit over the list (`Guide.toolkit`): a `Walkthrough` of `toolkitSteps` (what it adds; installing it from a clone of `github.com/BinaryBand/anywherellm-bridge`; printing the pairing link; and opening that link on the phone or scanning it drawn as a QR code). Where there is a scanner its end, Scan the pairing code, opens the Connection page with the camera reading.

**Companion addresses.** Where the toolkit, a companion, runs comes from a pairing code alone (`SettingsController.pair`); the app has no page to type one and guesses none, since whoever answered `/health` at a guessed address with the companion's name would get the key: a companion no code named is not looked for. An address is https, or http on a private network (`_companionAddress` in `parsePairingCode`), may hold a path prefix, and is kept in the keyring entry with the connection by `Companion.code` (`SettingsStore.save(Pairing(connection, companions))`; an entry an older version kept by a `/health` name is written again under the code, `companionKey`), kept when the key changes on the same server and forgotten for another server; `SettingsController.addressOf` is where each runs. A changed address makes that companion's `CompanionWatch` ask afresh there, so a companion reached through Cloudflare Tunnel or a proxy on a hostname of its own works.

**Connecting.** With nothing saved, Settings' Connection page (`ConnectionPage`, `ui/settings/connection_page.dart`) opens on the first run's welcome (`Headline`, `ui/widgets/headline.dart`: Connect to your AnythingLLM., the name in the accent), then Scan QR code first where there is a scanner, an or enter a key line (`_OrDivider`), the address and the developer key, each named small over its field (`NamedControl(quiet:)`), where to find a key (a link, Where do I find a key?, which opens How connecting works on its key screen: `showGuide(Guide.connect, step: 1)`), and Connect, which saves them through `SettingsController.connect` once `verify` passes. The key is a `SecretField` (`ui/widgets/fields.dart`): hidden until Show, which reads Hide after and is heard with the field's name, as Edit connection's key is. With the keyboard up (`KeyboardUp`, `ui/widgets/keyboard_up.dart`, which the shell provides since it takes the inset out of the media below it) Connect and the line above it leave the page for a bar of their own over the keyboard, with a `line2` rule over it, the page scrolls so the field in use sits just under the top fade (to its end when none has focus) until the person scrolls it, and the help link waits. The line for why a try failed takes room only while it has something to say. That opens How connecting works over the window while `ShellController.guide` is `Guide.connect` (an `OverlayWhile`, which brings the one opened last over the others, so it lies over the camera when `ScanView` opened it): a `Walkthrough` (`ui/settings/walkthrough.dart`) of `connectSteps`, three screens (the two things to bring, where the key comes from, and the address with the https rule). A `Walkthrough` is a pager of `GuideStep`s, swiped or stepped with the arrow keys; a figure is a `GuideFigure` (`ui/settings/guide_figures.dart`). Its last button scans a code where there is a scanner and otherwise closes it. A pairing code carries the address and a key, and may carry where the companions run (`&toolkit=...`, by its `Companion.code`); it is drawn by another AnywhereLLM or printed by the bridge's `anywherellm-bridge.cjs pair`, which makes or reuses the key named `AnywhereLLM`. Once a server is saved, the page holds a card of two `InfoRow`s (`ui/settings/rows.dart`): AnythingLLM server, with a Saved tag that reads Connected once Test connection has passed on this page, over the address in mono (left out while Edit connection is open), and Developer key, where it is kept; under it, while Edit connection has it open, the address and key fields with Save key and Scan QR code, and the camera whenever the shell is `scanning`; then, one under another, Test connection (`SettingsController.testSaved`, which verifies the saved connection), Edit connection (Cancel while editing) and Forget this server, which asks `Forget <host>?` in a sheet (`Popup.forgetServer`, a `SheetQuestion`) before it forgets. Another page, a new connection or a failed test puts back Saved. The address field is a URL field with the `url` autofill hint, and keeps suggestions on: Flutter on Android marks a field without suggestions as a visible password, which replaced the URL keyboard and invited a saved login; `AppField` leaves every other field out of autofill (null `autofillHints`), so the key is never offered a saved login, and a `private` field (the key's) turns off the keyboard's learning.

**Read aloud.** Each finished answer has Read aloud where there is `AppScope.readAloud`. `Speaker` (`ui/chat/speaker.dart`) is the port: `speak` resolves when the reading ends, finished or stopped, and throws when the device cannot speak. `ReadAloud`, in the same file, holds the one answer being read; it reads `splitReasoning`'s answer as `plainText` (`core/markdown.dart`: Markdown parsed, each block a line, a block of text alone one line), and stops when its answer leaves `ChatController.turns`, as when another chat, workspace or server shows. With `ChatSwitch.readAnswers` on, it reads each answer that ran to its end as it finishes, once, while that chat is on screen, when it has an answer beside its reasoning that is not a `modelFailure`: `ChatController.finished` is the last answer that was neither stopped nor failed, and `ReadAloud` takes the `PrefsController` to read the switch. `DeviceSpeaker` (`ui/chat/device_speaker.dart`, `flutter_tts`) is imported by `main.dart` only. It reads in pieces of at most 3500 characters (`speechParts`), since Android's engine refuses more than about 4000 at once. The manifest's `queries` lists `android.intent.action.TTS_SERVICE`. The web UI's server-side speech takes its login, not the developer key.

**Sharing into the app.** AnywhereLLM is a target of the system's share sheet: the manifest's `SEND` filters (`text/*`, `*/*`) and `launchMode="singleTask"`, so a share reaches the app already running. `androidShares` (`ui/share/android_shares.dart`, imported by `main.dart` only, which reads it once as a broadcast stream) gives each share as a `SharedItem`, as `Shares` (`android/.../Shares.kt`) hands it over the `anywherellm/shares` channel (`launchShare` for the one that started the activity, `share` for each later one): a shared file is a `content:` address read through the `ContentResolver` only when it is used (`read`), never written to a file, so the name the sharing app gives is only shown, after `plainFileName`; `Shares` refuses a `file:` path, a file the app's own providers serve, and a `content:` address whose authority holds user info, and ignores an intent the system replays from the recent apps (`FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY`), as `MainActivity` does a notification tap; what it hands over is (`ui/share/shared_item.dart`) a `SharedContent`, which is a `SharedLink` (`sharedTextItem` reads an address alone, or a title over one, as a link), `SharedText` or a `SharedFile` read only when used, or a `SharedPairing` (below). `AppScope.shares` hands each to `ShellController.showShared`, and the shell draws a `SharedContent` in `ShareSheet` (`ui/share/share_sheet.dart`) over everything but a popup: Share to AnywhereLLM Lite: the item, the workspaces with the open one first and chosen, then Add to documents (`addLink`, `addText` or `upload`, then Documents opens) or Ask about it: a new chat in that workspace with the link or the quoted text in the message, or the file attached (at most 20 MB, held to the bytes read as well as to the size the sharing app claims), put in the composer by `ChatController.putInComposer` for the person to ask; nothing is sent. Both open the chosen workspace first, and a sheet put away while a file is read opens nothing. With no server saved it says to connect first.

**Pairing links.** A tapped `anywherellm://connect?...` link opens the app: the manifest's `VIEW` filter (scheme `anywherellm`, host `connect`, `BROWSABLE`) hands it to `Shares`, which gives it as text, and `sharedTextItem` reads a pairing link alone as a `SharedPairing`, as it does one shared as text. The shell draws it in `PairingSheet` (`ui/settings/pairing_sheet.dart`) in `ShareSheet`'s place, since a link can come from any page or message: Connect to this server?, the server and the toolkit's address when the link names one, which saved server it replaces, then Cancel and Connect. Connect and a refused link work as they do for a scanned code (`ShellController.pairWith`, taken once by `takePairing`). The sheet shows each address whole, as every mono `InfoRow` does, on as many lines as it takes. The same filter takes `anywherellm://signed-in?service=<name>`, which library-lean's OAuth return page offers as a Back to AnywhereLLM button on Android once the provider sent a code back: `sharedTextItem` reads it, through `signedInOf` (`core/signed_in.dart`: a name as the skill allows one), as a `SharedSignIn`, and `_ShareListener` (`ui/shell.dart`) shows no sheet for it but the chat, with `I've signed in to <name>.` in the composer (`putInComposer`) for the person to send; nothing is sent. Any other `anywherellm:` link is read as a pairing, which says why it cannot be used. A link whose query is not valid UTF-8 is refused as not a pairing code (`parsePairingCode`) and reads as no sign-in (`signedInOf`). The manifest sets `flutter_deeplinking_enabled` to false, so Flutter never pushes the link to the Navigator as a route name.

**Memory.** While the toolkit serves `memories` (`ToolkitController.memories`), Settings' Memory page (`SettingsPage.memory`, `MemoryPage`, `ui/settings/memory_page.dart`) sits beside Server under AnythingLLM, its `parent` null; the workspace's pages have a Memory row under How it answers, both hidden otherwise, which shows that workspace (`MemoryController.show`) and opens it over them, so Back gives them back. `MemoryController` (`ui/state/memory_controller.dart`, built in `main.dart` over the `ToolkitApi`, the settings and `ChatController`) follows the open workspace until the page's Workspace chooser picks another, and starts afresh on another connection; the page reads it through `want`. It shows AnythingLLM's saved memories, which every chat is shown word for word, at most `globalMemoryLimit` (5) for every workspace and `workspaceMemoryLimit` (20) for each: the Workspace row (`Popup.memoryWorkspace`), the Saved memories and Learn from chats switches (`memorySwitches`, `setMemorySwitches`), then while on the lists of memories for every workspace and for only the open one, a full one saying so in place of Add a memory. A row opens the Saved memory sheet, keyed in the shell's popup by a `MemorySheet` so Back closes it: the memory's text, which workspaces it is Shown in, Delete (an existing memory only), which asks in the sheet (`SheetQuestion`), and Save. Every change reads the memories again, and a failed one shows over them, kept through that read. A memory gone from a read closes its sheet.

**Library and Vault.** anywherellm-suite's skills keep the agent off the person's own network (their fence) and refuse a private address at once; the person lets one through on the Vault page's Allowed addresses. While the toolkit serves `pages` (`ToolkitFeature.pages`, which its `/health` says as `pages: true`, since the route is the bridge's own), the toolkit's card has a row for each of library-lean's Library (its toolkits and runs) and the Vault that is set up. `GET /pages` at the bridge, with the developer key named `AnywhereLLM` (else 401 or 403), answers `{library, vault}`, each a root-relative path on AnythingLLM's address or null; `skillPagesOf` (`core/skill_pages.dart`) keeps a value only when it is that skill's page path (`isSkillPath`, `core/browser.dart`). A path is a bearer capability, since the page embeds its secret, so it is never logged, kept or persisted: `ToolkitController.pagesFound` holds only which `SkillPage`s are set up, read when the card shows (`wantPages`) and with the toolkit's other reads (`want`), and a card read that fails, a 401 or 403 among them, hides both rows and shows nothing. A tap reads `/pages` afresh (`pagePath`), hands the path it answers to `openAnswerLink`, which opens it in `PageSheet`, keeps it nowhere, and closes the shelf once the read is back; a page that answers null says `The <name> is not set up yet` in the chat's link notice and its row goes, and a failed tap says why there, a 401 or 403 hiding both rows. A token rotation changes the paths, so links in older answers then show `PageGone`.

**Activity and Upcoming.** The shelf has a card under the search (`ToolkitCard`, `ui/toolkit_card.dart`) with the Library and Vault rows above and a row for each of these the toolkit serves; Activity is built against a feature no route serves yet (`ToolkitFeature.activity`, never in `bridgeFeatures`), so only Upcoming shows. Each is a page over the chat (`ShellController.toolkitPage`, a `ToolkitPage`: `openToolkitPage`, `closeToolkitPage`), under `ToolkitPageFrame` (`ui/toolkit_page.dart`: Back, the title and its `action`, a round Read again or Upcoming's plus; it reads what the page shows as it opens, and `NotRead` says why a read failed, with Open Connection, or `Reading…`). The card reads what each serves the first time it shows on a server (`ToolkitController.want`; a read on its way is joined, not asked again), and its lines are what is in them: Activity `1 failed today` (`ToolkitFeature.activity`, `readActivity`) and Upcoming `3 tasks · next tomorrow 06:30` (`jobs`; worded `jobs` in place of tasks where the toolkit cannot change them). `ActivityPage` (`ui/activity.dart`) is read only; its rows open an app or file page through `openAnswerLink`, a picture in `ImageViewer`, or a chat through `ChatController.select`, and an event gone from a read closes its sheet (`ActivityOpen`, a `PopupSheet`). `UpcomingPage` (`ui/upcoming.dart`) reads the jobs afresh and lists each in one card: its name over `describeSchedule` (the cron in plain words in local time, with a weekly cron's day list or range named, as `Every Mon, Wed and Fri at 14:00` or `Weekdays at ...`, or marked UTC) and when it runs next or Off, or Last run failed in red, wrapped to four lines, then, with a server saved, Edit in AnythingLLM's web page, under Times are in your time zone. where the toolkit can change jobs and Read only here. where it cannot. Where the toolkit serves `jobs-write` (`ToolkitController.jobsWritable`) a round plus makes a task and a row opens its sheet (`TaskSheet`, `ui/task_sheet.dart`, a `PopupSheet` keyed in the shell's popup so Back closes it): `TaskDetail` shows the schedule and when it runs next, an On switch (`setEnabled`), Run now (`runNow`, which reads the runs again every 3 seconds while the latest is Running, up to 40 times, as `TaskDetail` does when it opens on a run still going, as after Edit and Cancel), Edit, what it does (its prompt, and how many tools it may use, which only AnythingLLM's web page sets), its latest runs (`JobRun`: its answer's text, or its `error`, read by `readRuns`) and Delete task, which asks with Keep and Delete and, like Save, closes only its own sheet, not a popup opened while it waited; `TaskForm` takes a name, what it should do, and Daily, Weekly or Custom (`Repeat`) with a time or day chips, or a cron, and a line under it from `ScheduleSpec.caption`. A daily or weekly time is sent as the UTC cron of today's offset, so it moves an hour when the clocks change; a custom cron is UTC; a cron that runs more often than every 5 minutes, or has a minute or hour out of range or too large to read (`cronProblem`), is refused before it is sent, though AnythingLLM would take it. AnythingLLM's jobs have no workspace and none runs once, so the form offers neither. A new job has no tools, and an edit leaves a job's tools as they are. Each change goes through `ToolkitController._change`, which reads the jobs again whether it went or not and shows why it failed over them (`changeProblem`, which goes with the next change, a later successful read of the jobs, or `clearChangeProblem`, which opening a task sheet calls: `openTask`, `ui/upcoming.dart`). A task gone from a read closes its sheet.

**Notifications.** The app posts two kinds of Android notification itself, with no UnifiedPush and no server pushing to it: `Answering in <workspace>`, the ongoing one of `AnswerService`, and a ready answer's, drawn by `Notes.kt` (`android/.../Notes.kt`, `ic_notification`, drawn by `tool/app_icon.dart`) on their own channels, Answering and Answers ready, so Android's settings can quiet each. `Notes.retire` deletes the channels an older version made (`anythingllm`, `apps`, `approvals`). There is no Notifications page in Settings. `MainActivity` asks Android for `POST_NOTIFICATIONS` once per run of the activity, when an answer first holds the app with the permission missing, and a notification the person refuses is dropped by Android. A tap on a ready answer's notification opens `MainActivity` with the chat's slug and thread, which it hands over the `anywherellm/background` channel (`launchTap` for the one that started the activity, `tap` for one while it runs) as `{slug, thread}`; `AndroidBackground` puts it in `BackgroundWork.taps` as a `ChatTarget` (`ui/chat/background_work.dart`), and `KeepAnswering` opens that chat (`ChatController.openTapped`), once the workspaces are read when the tap started the app, in place of `Prefs.lastChat`.

**Answers out of sight.** When the phone drops the stream, AnythingLLM (1.16.2) runs an agent answer, `automatic` mode's, to its end and saves it, since nothing on the server listens for the disconnect; a chat or query answer it stops (`abortConnectorOnClientDisconnect`) and saves what was written. `ChatController` therefore waits for a `CutOff` answer as above. `KeepAnswering` (`ui/chat/background_work.dart`, built in `main.dart` over the `BackgroundWork`, `ChatController` and `ShellController`) holds the app while `ChatController.working` (an answer runs or is waited for) through the `BackgroundWork` port: `AndroidBackground` (`ui/chat/android_background.dart`, imported by `main.dart` only) over `MainActivity`'s `anywherellm/background` channel, `hold` starting `AnswerService`, a `dataSync` foreground service whose ongoing notification says `Answering in <workspace>` (`Notes.ongoing`, a quiet `answering` channel), so Android neither ends the app nor cuts its connection out of sight; Android 15 ends it after 6 hours a day. Starting it once the app is out of sight is refused, and the answer goes on while it can. A service started that way must reach `startForeground` before it stops, or Android ends the app, so a release that comes first, as when an answer ends at once, is carried out by `onStartCommand` once it has. An answer finished while the app is out of sight (`AppLifecycleListener`) shows as a notification (`BackgroundWork.ready`, drawn by `Notes.ready`), titled with its chat; coming back to the front reads the waited-for answers at once.

**Adapters:**

- `adapters/anythingllm_client.dart` maps HTTP failures to plain-language `ApiException`s. Its own client connects within `connectTimeout` (10 s), less than the 15 s opening `timeout`, so a server that cannot be reached fails as a `SocketException` (`NotSent` for a question) and a timeout means one that took the request. No message may contain the key: an error the client does not map gets a fixed message with no error text, since a platform error can quote the header the key travels in; tests assert this, and `Connection.toString` omits it. `answerImage` is a bare `GET`, without the key, read whole within `timeout` between chunks, at most `maxImageBytes` (16 MB), of an address on the server's own host only (`loadableImage`); any other is refused unread (`offServerImage`).
- `adapters/anythingllm_stream.dart` turns a `stream-chat` response (server-sent `data:` lines) into `TextChunk`s, `StatusChunk`s, `WholeAnswer`s and one closing `ChatDone`; `chatEventsOf` reads the chunks once decoded. An `error` chunk fails the stream. Cancelling the subscription is how Stop ends an answer: `_events` reads the response itself rather than through `chatEvents`' `async*` readers, so the connection closes at once, even before the first chunk, and AnythingLLM stops answering; a tool already running may still finish on the server. An answer or a reset that sends nothing for `idle` (5 minutes) is let go of, since AnywhereLLM sends no pings; that and a dropped connection, once the answer's headers came, are a `CutOff`.
- `adapters/keyring_settings_store.dart` stores the address, the key and where its companions run as one JSON keyring entry; an entry an older version saved with a password is written again without it.
- `adapters/companion_client.dart` is `CompanionClient`, what every `Companion` takes: its `address` (`ConnectionHolder.addressOf`: where a pairing code said it runs, `ConnectionHolder.companions`, else null), its `/health` there without the key, remembered by that address until asked `again`, and JSON calls with the key under the address's path, refused unless `keySafe`, in plain words that name the companion and never hold the key (any other exception ends as `Could not reach <companion>.`, such as `Could not reach the toolkit.`, with no error text, and `_said`, the `error` a companion words a failure with, keeps its own closing `.`, `?` or `!`); a bare 404 or 405 is a `NoRoute`. `HttpToolkitApi` (`adapters/toolkit_client.dart`) is one over it; its features are what the `allow` list in its `/health` lets through, and what the bridge serves itself (`pages: true`).
- `adapters/json_prefs_store.dart` stores `Prefs` in the `File` it is given, `prefs.json` in `path_provider`'s application support directory, written to a temp file and renamed; a save made while another writes waits for it, and only the newest of the saves made meanwhile is written, since each holds everything.

**AnythingLLM API facts the client relies on:**

- `GET /v1/workspaces` gives each workspace's threads with their names but no documents. `GET /v1/workspace/{slug}` gives documents, and threads without names, as a one-item `workspace` array. Thread names therefore come from the list call; document counts cost one call per workspace.
- `DELETE /v1/workspace/{slug}` answers with no JSON, so it decodes with `emptyOk`, which accepts an empty body or a bare `OK`. It deletes the workspace's chats but leaves its documents in the library.
- Renaming a workspace is `workspace/{slug}/update` with `name`. `renameWorkspace` returns the workspace the server answers, and `ChatController` reads the workspaces again if its slug changed. AnythingLLM 1.16.2 keeps the slug.
- A chat is a thread: `thread/new`, `thread/{t}/update`, `DELETE thread/{t}` (empty body), `thread/{t}/chats` for history, `thread/{t}/stream-chat` for answers. The final stream chunk has `close: true` and the `sources` (the client does not read `close`: it ends at `finalizeResponseStream` or the end of the stream); a citation is matched to a file by its `title`. A source whose `chunkSource` is `link://https://...` is a web page an agent read; `citationsOf` keeps that address as the `Citation`'s `url`. A document added with `document/upload-link` has one too (`link://<url>`), so its citations carry its address; any other document's source has none.
- `stream-chat` is sent without `mode`, so a message answers in the workspace's own `chatMode`: `automatic` (Agent: tools when needed), `chat` or `query` (documents only), as in the web UI. A `mode` in the body overrides it, and the app sends one only for a message that carries a document while the workspace is `automatic` (`modeForFiles`, `core/chat.dart`, with the mode `SourcesController.chatMode` holds, which the composer passes to `ChatController.send`): `chat`, since AnythingLLM 1.16.2 reads a document attachment in only outside an agent run, and its agent sends every attachment to the model as an image (`formatMessageWithAttachments`), so a model shown an HTML page or a PDF that way sees nothing or fails. That message answers without tools. `@agent` in a message runs the agent whatever the mode.
- An agent answer streams `agentThought` chunks (`thought`, such as `@agent: Using SearXNG to search for ...`, or, when the provider is verbose, `` @agent is executing `web-browsing` tool {...} ``, read by `toolCall` as `Running web-browsing`) and `textResponseChunk` pieces that include what it wrote before and between tools. It then sends the whole answer as one `textResponse` chunk with `close: true`, and after it a `finalizeResponseStream` chunk with the `sources`: web results, dozens of them. A chat or query answer has its `sources` on the closing `textResponseChunk`, and its `finalizeResponseStream` has no text. Headers come at once, so the opening `timeout` holds even though the first text takes about 9 s. A query refusal is not stored in the history.
- There is no per-document switch. Switching a file off is `update-embeddings` with `deletes`, and the file is remembered in `Prefs.switchedOff` so Sources keeps listing it. An upload is `document/upload`, then `update-embeddings` with `adds` of each document's `folder/name` path (the folder of the returned `location` and the returned `name`). A web page is `document/upload-link` with `link`, and pasted text is `document/raw-text` with `textContent` and `metadata.title`; both answer `documents` as an upload does and are embedded the same way. Their `addToWorkspaces` field is never sent.
- All three take `metadata` with any of `title`, `docAuthor`, `description` and `docSource` (`DocMeta.toJson`, in `core/server_models.dart`), sent only when one is filled in, except for pasted text, which always sends its `title`. An upload sends it as a multipart field holding the JSON, which AnythingLLM 1.16.2 reads. Pasted text keeps its author, description and source, but the server stores its title as a file name, so `Meeting notes` comes back as `meeting-notes.txt`. There is no `/v1` call that changes details later.
- `stream-chat` takes `attachments` for one message: each is `name`, `mime` and `contentString`, a base64 data URL. `mime` is `image/*` for a picture and `application/anythingllm-document` for any other file, which the server's collector reads in for that message, outside an agent run, and puts in the context; the data URL carries the file's own type for `.pdf`, `.txt`, `.md`, `.csv`, `.html`, `.json`, `.docx`, `.xlsx` and `.pptx`, else `application/octet-stream`. A file the collector cannot read is dropped with a line in the server's log, and the message goes without it. A history entry lists `attachments` for images, with the `contentString` it was sent with, but not for documents. `ChatMessage.attachments` keeps each as a `SentFile` (`core/server_models.dart`): its name and, for a picture, the data URL, decoded only the first time `picture` is read, so reading a history for its ids costs no decoding. A sent `Turn` keeps the picture's bytes the same way, and the question shows it small.
- The server's slash commands are not used. `stream-chat` swaps each server preset for its prompt itself, so one typed is sent as typed, and `/reset` sent as text reaches the model, since the `/v1` handler never checks the built-in commands. The preset list (`GET /api/system/slash-command-presets`, which takes the web login) is left alone. The app's own `/reset` clears a chat with `stream-chat` and `{"reset": true}` and no message (`AnythingLlmApi.resetChat`), which marks that thread's chats `include: false` and answers one `Chat history was reset!` chunk: the model no longer sees them and the history call no longer lists them, here or in the web UI. The server keeps the rows and no call brings them back.
- Developer keys (`/api/system/api-keys`, `/api/system/generate-api-key`) take the web login, so the app does not use them; the toolkit's `pair` does.
- Saved memories and scheduled jobs take the web login, so the app reaches them through the toolkit's bridge, with the developer key. `HttpToolkitApi._json` fails an answer with `success: false`, which AnythingLLM sends with HTTP 200, in its words. The bridge passes a call to AnythingLLM's internal `/api/<path>` when a rule in its owner's `BRIDGE_ALLOW` permits it, with AnythingLLM's status and JSON as they are, and refuses any other with 403 and `{error}`. A rule is `[METHOD ]/prefix`; a prefix matches whole segments, a `*` in it takes any one segment (`GET /workspace/*/thread/*/chats`), and a rule with no method allows `GET`, `POST`, `PUT` and `DELETE`. `GET /health` answers `{ok, service, allow}`, the rules as text. Everything the app uses passes with the toolkit's `CLIENT_ALLOW`, which its `install` writes as `BRIDGE_ALLOW` when that is unset (`liteBridgeAllow` in `test/support/fake_toolkit.dart`): `/workspaces, /memories, GET /admin/system-preferences-for, POST /admin/system-preferences, /scheduled-jobs`. The routes, as AnythingLLM 1.16.2 answers them: `GET /admin/system-preferences-for?labels=memory_enabled,memory_auto_extraction` (`{settings}`, each as text; learning is on unless `"false"`) and `POST /admin/system-preferences` (`{"memory_enabled": "true"}`); `GET`/`POST /workspaces/{slug}/memories` (`{memories: {global, workspace}}`, each `id`, `content` and `scope`; a post `{content, scope}`), `PUT /memories/{id}` (`{content}`), `POST /memories/{id}/promote` (for every workspace) and `POST /memories/{id}/demote/{slug}` (for one), each answering `memory`, and `DELETE /memories/{id}` (`{success}`); `GET /scheduled-jobs` (`{jobs: [{id, name, prompt, tools, schedule, enabled, lastRunAt, nextRunAt, latestRun}]}`, `tools` JSON text or null, the cron and times in UTC, no workspace), `GET /scheduled-jobs/{id}/runs` (the newest 50, `{runs: [{status, result, error, startedAt}]}`, `status` `queued`, `running`, `completed`, `failed` or `timed_out`, `result` JSON text holding the answer's `text`), `POST /scheduled-jobs/new` (`{name, prompt, schedule}` from the app, which leaves out `tools`, though the server takes them; answering 201), `PUT /scheduled-jobs/{id}` (any of `name`, `prompt`, `tools`, `schedule`, `enabled`), `DELETE /scheduled-jobs/{id}` (`{success}`, false for an unknown id) and `POST /scheduled-jobs/{id}/trigger` (`{success, skipped}`, skipped while a run of it is queued or running; it answers at once). AnythingLLM checks only that a cron parses, keeps no job that runs once, and takes no idempotency key. The scheduled-job routes answer only in single-user mode. A refusal is `{error}` in AnythingLLM's words (a full list: `Maximum global memory limit (5) reached.`). While memories are off the memory routes answer 403 (`Personalization is disabled.`), so `MemoryController` reads the switches first.
- Exchanges: a `/v1` history entry (`convertToChatHistory`) carries `chatId` on both the question and the answer; the closing `finalizeResponseStream` of a chat or query answer carries the new `chatId`, and an agent answer's closing chunk has none (AnythingLLM's `apiChatHandler.js`). Deleting a thread's exchanges (`delete-edited-chats`) and marking an answer (`chat-feedback`) take the web login, so the app does neither.
- `POST /v1/workspace/{slug}/vector-search` with `query` answers `results`, each a passage `text`, a `score` from 0 to 1 and `metadata.title`; with no `topN` or `scoreThreshold` it uses the workspace's own, as an answer does. An empty query is a 400. `GET /v1/workspace/{slug}/chats` lists only chats outside any thread and is not used.
- `"Unknown"` is a server placeholder, read as absent. An upload can answer HTTP 200 with `success: false`; `_decode` fails any answer with `success: false`, whatever its status.
- `GET /v1/workspace/{slug}` also carries `openAiPrompt` and the settings columns in `workspaceSettingSpecs` (type and bounds), and each document's `pinned`, which the app does not read. `POST workspace/{slug}/update` takes any of those columns and answers `workspace: null` with a `message` when it refuses.
- A document's `folder/name.json` path is what workspaces use. `GET /v1/document/{name}` takes the file name alone and may leave out `pageContent`.
- `GET /v1/system` gives `settings` with secrets replaced by booleans; a real on-off setting such as `AgentSkillRerankerEnabled` is a boolean too, so the app cannot tell the two apart by value: `settingText` reads any boolean as no text, and an on-off setting is read by its own key. `POST /v1/system/update-env` writes the `.env` from `KEY_MAPPING`'s names. It drops an unknown key or an all-asterisk value without a word, stops at the first failed check with the keys before it already written, and answers `newValues` and `error` with HTTP 200, so `updateSystem` fails on an `error` or on any key sent that is not in `newValues`. `GET /v1/system/vector-count` counts the whole server.
- The closing chunk of an answer, and each history entry, carry `metrics` (`completion_tokens`, `duration`, `outputTps`, `model`, and `inputCost` and `outputCost` when priced; `{}` when unmeasured) and, for an agent, `outputs`: each `{type, payload: {filename, storageFilename, fileSize}}`, `imageGenerationCard` for an image and `PdfFileDownload` and the like for a file. `GET /v1/document/generated-files/{storageFilename}` answers the bytes, an HTML file as `text/html` with `Content-Disposition: attachment`, which `_file` takes where it would refuse the web UI's own page; `generatedFilesOf` keeps only a storage name of letters, digits, `_`, `.` and `-`, and not dots alone.

**UI:**

- `ui/app_scope.dart` is an `InheritedWidget` that never notifies. It holds the controllers, `launch` (a `LinkOpener`), `save` (a `FileSaver`) and the device's features (`scanner`, `share`, `shares`, `dictation`, `photos`, `readAloud`, `appView`, `background`), each null where the device has none, as tests pass them; `main.dart` passes all of them. `DevicePhotos` (`ui/chat/device_photos.dart`, `image_picker`) is the `PhotoPicker`. `canSpellcheck` says whether the platform has a spell checker (`main.dart` reads `platformDispatcher.nativeSpellCheckServiceDefined`); only then does the composer spellcheck, while `ChatSwitch.spellcheck` is on, and does Settings' Chat page show the switch. `enterSends` says whether Enter sends the message, true on Linux, macOS and Windows. Widgets wrap the controller they read in a `ListenableBuilder`, and `AppScope.of` is safe in `initState`. `main.dart` passes `url_launcher`'s `launchUrl` as `launch`, so `url_launcher` is imported there only: an http or https link opens in the in-app browser (`LaunchMode.inAppBrowserView`: a Custom Tab over the app, which Back closes, or the plugin's own web view where no browser offers Custom Tabs), and a `mailto:` link, which that mode refuses, in the app the system picks. `ui/links.dart`'s `openLink` opens only what `openableLink` allows (http, https, mailto, and a path from the root, such as browser-lean's `/browser-lean/<token>.html`, on the connected server's origin as AnythingLLM's own chat reads it: `onServer`, `core/chat.dart`) and reports anything else, or a link nothing opened, as `ChatController.linkNotice`. `save` is `saveWithPicker` (`ui/files/save_android.dart`, `file_picker`), the storage access framework's save dialog, which takes the bytes with it, so `saveFile` (`ui/files/save_file.dart`) fetches first; a failure shows in the workspace's pages or the problem the caller names. `saveFile` and `shareFile`, which every save and share goes through, take the name as a `plainFileName` (`core/files.dart`: a character a file name cannot hold, `/` and `\` among them, made `-`, and one of dots alone replaced), since `share_plus` writes the bytes to a file of that name. Files to attach or add are picked with `file_picker` too.
- `ShellController` (`ui/state/shell_controller.dart`) holds what is open over the chat, which is always the base: `openChat` shows it again, closing the shelf, the sheet, the popup, Settings and what lies over it; the shelf the chats show in (`shelfOpen`, `openShelf`, `closeShelf`), the sheet (`rightOpen`, showing a `Beside`: Sources, an answer's passages from the sources list, or all of an answer's sources, over the chat or the workspace's pages; a document's text opened from the Documents sheet takes its place, `showDocText`, and gives it back when it closes, `textClosed`), Settings and its page (`openSettings(page)` opens a page over what shows, so Back from a page with no `parent` gives that back, and `openSettings()` opens the list over the chat with nothing else open, as the shelf's Settings row does), the `Pane` (the chat, or the workspace's pages, with `workspacePage`), a page of the toolkit's over the chat (`toolkitPage`: Activity or Upcoming), `scanning`, the walk-through shown (`guide`, a `Guide`), what another app shared, and `popup`, the one popup open: a `Popup`, a `Turn` whose More sheet is open, a `Citation` whose passages show, a `GalleryOpen`, a `ChatSheetFor`, a `WorkspaceSheet`, a `MemorySheet`, a `BrowserOpen` or a `PageOpen`, opened with `togglePopup` and closed with `closePopup`; it notifies apart from the shell, so a popup rebuilds only what listens to it.
- There are no routes. `ui/shell.dart` is a stack, with no bar of tabs; the sheets, `ShareSheet` and the popups lie over the whole window. What shows stacks, from the bottom: the chat (`ChatView`), the base screen and what the app opens on, always built and offstage while the workspace's pages, a page of the toolkit's or Settings cover it, so a draft and a running answer survive; the chats as a shelf (`ChatsShelf`, `ui/shelf.dart`, which holds `ChatsList` over a Settings `NavRow` at its foot, with the `gear` icon apart from Workspace settings' sliders, which opens Settings' list) while `shelfOpen`; in `Pane.files`, the workspace's pages (`WorkspacePages`); a page over the chat (Upcoming); the deleted chat's floating undo (`UndoBar(floating:)`, over the chat's composer); the sheet (a `SheetFrame`, `ui/widgets/sheet.dart`; its scrim, a drag down past 120 px or a fling close it); Settings, its list or a page over what showed; `ShareSheet`; then the popups. - `ChatController` keeps the workspaces, each workspace's threads, the turns of each opened chat and the answers running (`_runs`, each a `_Running`: its turn, its workspace, its thread, its stream). One answer runs at a time in each chat, and chats of one workspace answer at once, since AnythingLLM keeps each run's history and saved answer by its thread. `busy` says whether the chat on screen can take no message: it answers, messages wait for it to end (`onDeck`), or its history is being cleared (`reset`); clearing one chat's holds back no other. `stop` stops the chat on screen's answer by letting go of it. A pull down past the oldest turn (`PullRefresh`, `ui/widgets/pull_refresh.dart`, with `AlwaysScrollableScrollPhysics` so a short chat pulls too) is `ChatController.refresh`: it reads the workspaces and the chat on screen again (`open(again: true)`), for a lost connection; an answer still running in that chat is let go of first and stays unfinished with why until the server's copy is read, and a chat deleted elsewhere gives way to its workspace's newest chat, or a draft. A chat whose last answer failed, was stopped or is waited for (`Turn.unfinished`) is read again the next time it is opened, so what the server saved shows. An answer whose stream ends in a `CutOff` is not failed but `Turn.waiting`: it shows Still answering on the server with Check now (`checkWaiting`) in place of Ask again, Retry is off, and the chat's history is read (`ChatController.waits`, an `AnswerWaits`, `ui/state/answer_waits.dart`) every 5 s, then every 20 s after 2 minutes, until its last entry is the answer, which then replaces the chat's turns, counts as `finished` (`finishedIn`) and as ready elsewhere; after `AnswerWaits.waitReads` reads (30 minutes) it fails, and a chat that moved on stops the reading and says the answer is missing, to be read with a pull down. A new wait in a chat already waited for ends the older one as moved on, and a read that fails in any way counts as a failed read and the polling goes on. The answer is the first exchange newer than the newest the server had saved in that chat (`ChatController._newest`), learnt from every history read, which never moves it back, and from a chat or query answer's closing `chatId`; an agent answer's closing chunk names none, so one that ran to its end costs one history read for it, and a stopped or failed one leaves it unknown, since the server may still save that answer. With it unknown, an exchange counts as the answer once it is newer than the newest a read before it found, or, before any read found one, once it is newer than every exchange the chat showed and asks the waited question as many times as the chat does. A history read that began before a message was sent, or an answer settled, in that chat is dropped when it returns. `load` keeps a chat made, or answering, after its read began, which that read may not list. A list of turns it has handed out is never changed afterwards; every change sets a new list, because `MessageList` may still be drawing from the old one. A `Turn` (`ui/state/turn.dart`) is itself a `ChangeNotifier` that takes each streamed `ChatEvent` (`take`): a chunk notifies only that turn, so only its answer rebuilds. A chat not yet asked anything is a draft held only in the controller; its first message creates the thread, and when the answer to that message ends, however it ends (Stop while the thread is still being made too), the chat is renamed with `defaultTitle` unless the person renamed it. A chat that already existed keeps its name, even after it is retried or edited back to no question.

The text's Download saves `DocBody.text` under `textFileName` (`core/files.dart`) through `saveText` (`ui/files/save_file.dart`), reading the text through `FilesController.textOf`, and shows a failure, or a document the server sent no text for, in Sources' problems, which the sheet shows when the text closes. The server keeps only the text it read, never the uploaded file, so `report.pdf` saves as `report.pdf.txt`.
- The workspace's pages (`WorkspacePages`, `ui/files/workspace_pages.dart`, in `Pane.files`, opened by the shelf's Workspace settings or the header on a new chat): a Workspace page (`PhonePageHeader`) with a `SummaryCard` and rows for Documents, Instructions, Answer from and Memory, then Delete workspace, which is off while an answer runs in it (`ChatController.answeringIn`). Instructions is the `PROMPT.md` editor, which says when it is empty that the server's default applies (an empty prompt is sent as null), with Revert and Save once the text has changed. Answer from is `SettingsForm` (`ui/files/settings_form.dart`): a `RadioCard` for each mode, Chat model, a row that opens `ModelPicker`, and When the files do not cover it; the rest is kept as the server has it, and Revert and Save show once something changed. `FilesController` (`ui/state/files_controller.dart`) backs them: it keeps the `FilesSection` shown (`openSection`) and the workspace it shows, follows another workspace opened while they show (`ensureLoaded`) and catches up when they show again (`hidden`), takes each workspace as Sources last read it (`SourcesController.read`, `detail`), and saves through `save`, which writes `openAiPrompt` or the settings that differ (`parseSettings`: `chatMode` only as `automatic`, `chat` or `query`, never null; a value left as the server had it is not checked or sent). It reads the workspace again after a save and hands it to `SourcesController.show`, forgets a deleted workspace, and shows a re-read that fails after a change in its problems.
- Settings is `SettingsDialog` (`ui/settings/settings_dialog.dart`): its list shows over the chat, opened from the shelf's foot, and a page shows over what showed. The list holds, once a server is saved, a `SummaryCard` with AnythingLLM, whether it answers (`Testing…`, Connected, Not answering when Test connection failed, or Connection problem when the last read of the workspaces failed, `ChatController.unreachable`) and its host in mono, and Test connection; then This app (Connection, Appearance and Chat, each with an icon) and AnythingLLM, with Server (`serverSummary`: the chat model and the passages stored), and Memory while the toolkit serves `memories`, then, while the toolkit serves nothing, the Get more from your server card. Settings reads the server's settings afresh each time it opens (`SystemController.readSettings`, which a second ask joins), and Server and Privacy and data read them only when they are not read yet (`wantSettings`), both through `ServerSettings` (`ui/settings/server_settings.dart`), which shows why a read or save failed. `ShellController.settingsPage` is the page shown, null for the list; `openSettings([page])` opens Settings, and the composer's server link, the no-key banner and a start with nothing saved open `SettingsPage.connection`. - Appearance and Chat (`ui/settings/device_pages.dart`) hold what lives in `prefs.json`. - Privacy and data (`PrivacyPage`, `ui/settings/privacy_page.dart`) shows the chat model, document search model and document storage the server uses, read-only, each with where it runs or what it is shared under (`chatModelPrivacy` names the host of the provider's address with its port, never a login, and reads an address written without a scheme as http: the server's own, a private network's by the rule the key follows (`isPrivateHost`, and Docker's names under `.internal`), or a service's), and an Anonymous telemetry switch, which writes `DisableTelemetry` through `SystemController.saveSettings`, the app's only write to the server's settings. `SystemController` (`ui/state/system_controller.dart`) owns what these pages read from the server rather than a workspace: the settings and the vector count; a new server clears it.

## Conventions

- Dependencies in `pubspec.yaml` are pinned by series (`">=1.6.0 <1.7.0"`). Moving to a newer series is a deliberate edit.
- Doc comments state what a thing is or does, in plain sentences, with `[name]` references. Match that density in new code.
- Every file that is a source of truth for an app or service (its log, `app.json`, its reducer, a playbook) can be viewed raw in the app. Secrets are the exception: the app names them and never shows their value.
- Cache files are never shown. A value derived from them may be, labelled as derived, as long as it can be rebuilt from files the app shows.
