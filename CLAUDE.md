# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

AnywhereLLM is a Flutter chat client for Android phones for an AnythingLLM server. It shows workspaces and their chats (AnythingLLM threads), streams answers, and manages each workspace's documents, instructions and answer settings in the workspace's pages. Where the anythingllm-apps-v2 server runs beside AnythingLLM, it also shows and manages the agent's apps. Through a UnifiedPush distributor it shows AnythingLLM's scheduled-job pushes and the apps' `notify` pushes as Android notifications. It keeps the server address and API key in the Android Keystore and its other preferences in a JSON file. It calls AnythingLLM's own API, and the apps server's when there is one, directly, over https only; there is no backend of its own.

## Commands

```bash
flutter pub get
flutter analyze
flutter test                                   # whole suite; fakes the server and the keyring
flutter test test/ui/shell_test.dart           # one file
flutter test --plain-name 'a new server starts afresh'   # one test by name
flutter run -d <android-device>                # a phone over adb, or an emulator
flutter build apk --debug                      # -> build/app/outputs/flutter-apk/app-debug.apk
flutter build apk --release                    # needs android/key.properties
flutter test tool/store_graphics.dart          # store graphics -> build/store/en-US, or $STORE_GRAPHICS
flutter test tool/screens.dart                 # each screen at 390x844, light and dark -> build/screens, or $SCREENS
flutter test tool/app_icon.dart                # icon pictures -> assets/icon, and the notification icon
```

A release APK is signed with the key named in `android/key.properties` (gitignored), which the personal F-Droid repo's `appstore sync` writes the first time it builds the app. Without that file the release build fails rather than signing with the debug key, because every later update must carry the first release's key. `android.enableResourceOptimizations=false` keeps the launcher icon at the path fdroidserver reads, and `allowBackup` is off so a restored backup never carries a Keystore-encrypted key to a device that cannot decrypt it. Its launcher icon and launch screen are made from `assets/icon` (`icon.png`, `icon-foreground.png` for the adaptive icon, `splash.png`), drawn by `flutter test tool/app_icon.dart` from the robin mark (`RobinMark`, `lib/ui/widgets/robin_mark.dart`, which the logo tile beside the wordmark draws too: the logo study AnywhereLLM Ribbon Trim's angular tail with no spike, in its own units, placed on the 1024 unit box by `_place`) in the design canvas's icon colours, `iconGround` (`#4B5DC3`) and `iconInk` (white), with the `#F2853D` breast. After changing them, run `dart run flutter_launcher_icons` and `dart run flutter_native_splash:create` (configured in `flutter_launcher_icons.yaml` and `flutter_native_splash.yaml`) and commit the generated resources. It needs the Android SDK; `minSdk` is Flutter's default (24), which is what `flutter_secure_storage` requires.

The F-Droid store page's feature graphic and phone screenshots come from `tool/store_graphics.dart`, which draws them with the app's own fonts over the test fakes, so no real server shows; copy `build/store/en-US` to `metadata/local.anywherellm.lite/en-US` in the app_store project (its `phoneScreenshots` replaced whole, since the store lists every file there, and its `icon.png` kept, since the tool does not draw it), whose `appstore.toml` holds the listing text, and run `appstore sync` there.

## Naming

- The product on this branch is **AnywhereLLM Lite**, published in the personal F-Droid repo as a separate app from AnywhereLLM (`master`): launcher label `AnywhereLLM Lite` (`android/app/src/main/AndroidManifest.xml`) and application ID `local.anywherellm.lite` (`applicationId` in `android/app/build.gradle.kts`). The Kotlin `namespace` stays `local.anywherellm.anywherellm`, which only names the generated classes. The store builds it from a clone at `~/Dev/Apps/anywherellm_lite` kept on this branch, so that clone's `android/key.properties` holds Lite's own release key. The Dart package is `anywherellm`, so imports are `package:anywherellm/...`. The repository folder is still `everything`.
- `flutter_secure_storage` keys its keyring entry by the application ID. Changing `applicationId` orphans any saved key.

**The connection** lives in one shared `ConnectionHolder`, built in `main.dart`. `HttpAnythingLlmApi` reads it on every call, so a saved connection takes effect without a restart. `SettingsController` is the only writer, through `load`, `save` and `clear`, which notify listeners. `ChatController` listens and starts afresh when the connection changes; `SessionHost` builds it before reading the keyring, so reading a saved connection is what loads the workspaces. `verify(Connection)` takes an explicit connection so Settings can test one before saving; `SettingsController.connect` verifies first and saves only on success.

**https, or http on a private network.** Dart's `HttpClient` ignores Android's cleartext policy, so the app keeps its own rule (`keySafe`, `isPrivateHost` in `core/connection.dart`): the key goes over https anywhere, and over plain http only to a private host: `localhost`, a name with no dot, a name under `.local`, `.lan`, `.home.arpa` or `.ts.net`, an IPv4 address in `127/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16` or Tailscale's `100.64/10`, or IPv6 `::1`, `fc00::/7` or `fe80::/10`. `normalizeBaseUrl` refuses any other http address (`plainHttpRefused`), every call and `verify` check it again before the key is sent (`_secure`), and the same rule decides an answer's image, a companion's address and an app page in the web view; the manifest's `usesCleartextTraffic` lets Android load such a page. A saved http connection (`Connection.plainHttp`) shows a Plain http warning on the Connection page.

**Scanning a pairing code.** Scan QR code on Settings' Connection page reads a code another AnywhereLLM drew, `anywherellm://connect?url=...&key=...`, with `AppScope.scanner`; `parsePairingCode` reads it, the fields are filled, and the card saves through `connect` as for a typed key. A scanned key the server refuses shows in the key field, under why. The scanner is `cameraScanner` (`ui/settings/scan_code.dart`, `mobile_scanner`), imported by `main.dart` only; tests pass a fake or null, and with none there is no Scan button. The camera shows in `ScanView` (`ui/settings/scan_view.dart`), a page over the window under Back, heard as Cancel, with the camera in a square as wide as the screen, where to find the code and How connecting works; whether it is open is `ShellController.scanning`, which Esc and Back stop first. `mobile_scanner` bundles Google ML Kit (`libbarhopper_v3.so`, not free software) and adds about 17 MB to the release APK; its manifest adds the CAMERA permission with the camera marked optional.

**Dictation.** The composer has a microphone where there is `AppScope.dictation`. `Dictation` (`ui/chat/dictation.dart`) is the port: `start` gives the words heard so far in full each time and calls `onDone` once when listening ends, with the `DictationEnd` that ended it: `stopped` by `stop`, `paused`, or `failed`. `SpeechDictation` (`ui/chat/speech_dictation.dart`, `speech_to_text`) is imported by `main.dart` only. What is heard follows the message as it stood when listening began. A change to the message made otherwise, by typing, a suggestion or Edit, ends the go and is kept. Sending ends the go, and words that arrive after it are dropped. `done` ends a go, not `notListening`, which comes before the last words. With `ChatSwitch.sendDictation` on, a go that ended `paused` sends the message when `canSend` (`ui/chat/composer.dart`) allows it, the same check the Send button makes; a go the person stopped or that failed leaves the message in the box. The manifest adds `RECORD_AUDIO` with the microphone marked optional and a `queries` entry for `android.speech.RecognitionService`; recognition runs in the device's own service, which may send the audio to its maker.

**The developer key alone.** The app reaches AnythingLLM through its developer API (`/api/v1`) with the developer key, and never signs in to the web UI. What only the web login opens (`validatedRequest`: deleting a thread's exchanges, marking an answer, saved memories, scheduled jobs, AnythingLLM's own web push, developer keys, slash-command presets) the app leaves alone, or reaches through the toolkit when it runs beside the server (Memory and Upcoming). So Retry and Edit leave the old exchange on the server beside the new one, and an answer cannot be rated. `Connection` is the address and the key alone; `KeyringSettingsStore` writes an entry an older version saved with the server's password again without it. **Companion addresses.** Where each companion, the apps server and the toolkit, runs comes from a pairing code alone (`SettingsController.pair`); the app has no page to type one, and one no code named is guessed (`Companion.base`). **Notifications.** The apps server pushes each app's `notify` as Web Push (RFC 8030, encrypted for the device, RFC 8291), which reaches the phone through a UnifiedPush distributor such as ntfy; the device needs one installed. Notifications are on exactly while UnifiedPush has a distributor saved, so the app keeps no switch of its own. `PushController` (`ui/state/push_controller.dart`, built in `main.dart`) keeps each `PushSource` (now `apps` alone, its own UnifiedPush instance and Android channel, Apps) registered with its server's VAPID key, `pushKey`, whenever the server in use or whether the apps server is there changes, and at every start; the endpoint the distributor answers goes to that server's `subscribePush`. AnythingLLM's own web push takes its web login, so the app does not use it; `UnifiedPusher` unregisters the instance an older version used for it (`anythingllm`) at start, unawaited after the launch tap, and `PushNotes.retire` deletes its Android channel. The apps server's are `GET /push/key` (`{key}`), `POST /push/subscribe` and `POST /push/unsubscribe` (`{endpoint}`), with the key, offered while its `/health` names `push` (`AppsController.serves(AppsFeature.push)`). Turning on asks Android for `POST_NOTIFICATIONS`, then uses the saved or default distributor, the only one installed, or asks which (`choices`); with none installed it says to install one. Turning off unsubscribes from the apps server and unregisters every source. The apps server sends `{title, body, data}`, its `data` the app's `workspace` and `app`. `tapTargetOf` reads a tapped one by its channel: an app's opens the app it names (`appRefNamed`) in its sheet. `Pusher` (`ui/push/pusher.dart`) is the port and `UnifiedPusher` (`ui/push/unified_pusher.dart`, `unifiedpush_android` and its platform interface alone, since the `unifiedpush` package's Linux plugin brings webcrypto, which does not build for Android) the device's, imported by `main.dart` only. Android shows each push natively: `PushEvents` (`android/.../PushEvents.kt`) replaces the plugin's `UnifiedPushService` in the manifest (`tools:node="remove"`), since that service starts a Flutter engine for a push only when no plugin was ever made in the process, which leaves a push unshown after Back closed the activity. `PushNotes.kt` draws it (`ic_notification`, drawn by `tool/app_icon.dart`) on its source's channel, and `PushEvents` hands the distributor's other events to the plugin's `Plugin.calls`, which keeps the last 20 for a Dart side not yet listening. A tap opens `MainActivity` with the source and the payload, which hands them over the `anywherellm/push` channel (`launchTap`, `tap`), where `askPermission` is too. `android/app/build.gradle.kts` substitutes `tink-android` for the connector's `tink`, which `flutter_secure_storage`'s duplicates.

**Answers out of sight.** When the phone drops the stream, AnythingLLM (1.16.2) runs an agent answer, `automatic` mode's, to its end and saves it, since nothing on the server listens for the disconnect; a chat or query answer it stops (`abortConnectorOnClientDisconnect`) and saves what was written. `ChatController` therefore waits for a `CutOff` answer as above. `KeepAnswering` (`ui/chat/background_work.dart`, built in `main.dart` over `ChatController`) holds the app while `ChatController.working` (an answer runs or is waited for) through the `BackgroundWork` port: `AndroidBackground` (`ui/chat/android_background.dart`, imported by `main.dart` only) over `MainActivity`'s `anywherellm/background` channel, `hold` starting `AnswerService`, a `dataSync` foreground service whose ongoing notification says `Answering in <workspace>` (`PushNotes.ongoing`, a quiet `answering` channel), so Android neither ends the app nor cuts its connection out of sight; Android 15 ends it after 6 hours a day. Starting it once the app is out of sight is refused, and the answer goes on while it can. An answer finished while the app is out of sight (`AppLifecycleListener`) shows as a notification on the `answersChannel` (`answerReadyPayload`, drawn by `PushNotes`), titled with its chat, which opens it (`ChatTarget`, through `tapTargetOf` and `PushController`); coming back to the front reads the waited-for answers at once.

**Adapters:**

- `adapters/anythingllm_client.dart` maps HTTP failures to plain-language `ApiException`s. No message may contain the key; tests assert this, and `Connection.toString` omits it. `answerImage` is a bare `GET`, without the key, read whole, at most `maxImageBytes` (16 MB).
- `adapters/anythingllm_stream.dart` turns a `stream-chat` response (server-sent `data:` lines) into `TextChunk`s, `StatusChunk`s, `WholeAnswer`s and one closing `ChatDone`; `chatEventsOf` reads the chunks once decoded. An `error` chunk fails the stream. Cancelling the subscription is how Stop ends an answer: `_events` reads the response itself rather than through `chatEvents`' `async*` readers, so the connection closes at once, even before the first chunk, and AnythingLLM stops answering; a tool already running may still finish on the server. An answer or a reset that sends nothing for `idle` (5 minutes) is let go of, since AnywhereLLM sends no pings; that and a dropped connection, once the answer's headers came, are a `CutOff`.
- `adapters/keyring_settings_store.dart` stores the address and the key as one JSON keyring entry; an entry an older version saved with a password is written again without it.
- `adapters/companion_client.dart` is `CompanionClient`, what every `Companion` takes: its `address` (`ConnectionHolder.addressOf`: where it was said to run, `ConnectionHolder.companions`, or else `Companion.base`'s guess), its `/health` there without the key, remembered by that address until asked `again`, and JSON calls with the key under the address's path, refused unless `keySafe`, in plain words that name the companion and never hold the key; a bare 404 or 405 is a `NoRoute`. `HttpAppsApi` and `HttpToolkitApi` (`adapters/toolkit_client.dart`) are each one over it.
- `adapters/apps_client.dart` is `HttpAppsApi`, the `AppsApi` over the apps server's client API, reading the same `ConnectionHolder`; it sends the key only to `/apps/` routes, refuses an `http://` server before sending it, and never puts the key in a message. A 404 or 405 without the server's `error` is a route an older apps server lacks (`NoRoute`): `app` and `log` then answer null, remembered per connection and route (`_missing`) until `available(again: true)`. `card` is a bare `GET`, with `If-None-Match` when given the last `CardPicture`, whose picture it answers on a 304.
- `adapters/json_prefs_store.dart` stores `Prefs` in the `File` it is given, `prefs.json` in `path_provider`'s application support directory, written to a temp file and renamed; a save made while another writes waits for it, and only the newest of the saves made meanwhile is written, since each holds everything.

**AnythingLLM API facts the client relies on:**

- `GET /v1/workspaces` gives each workspace's threads with their names but no documents. `GET /v1/workspace/{slug}` gives documents, and threads without names, as a one-item `workspace` array. Thread names therefore come from the list call; document counts cost one call per workspace.
- `DELETE /v1/workspace/{slug}` answers with no JSON, so it decodes with `emptyOk`, which accepts an empty body or a bare `OK`. It deletes the workspace's chats but leaves its documents in the library.
- Renaming a workspace is `workspace/{slug}/update` with `name`. `renameWorkspace` returns the workspace the server answers, and `ChatController` reads the workspaces again if its slug changed. AnythingLLM 1.16.2 keeps the slug.
- A chat is a thread: `thread/new`, `thread/{t}/update`, `DELETE thread/{t}` (empty body), `thread/{t}/chats` for history, `thread/{t}/stream-chat` for answers. The final stream chunk has `close: true` and the `sources`; a citation is matched to a file by its `title`. A source whose `chunkSource` is `link://https://...` is a web page an agent read; `citationsOf` keeps that address as the `Citation`'s `url`. A document added with `document/upload-link` has one too (`link://<url>`), so its citations carry its address; any other document's source has none.
- `stream-chat` is sent without `mode`, so every message answers in the workspace's own `chatMode`: `automatic` (Agent: tools when needed), `chat` or `query` (documents only), as in the web UI. A `mode` in the body would override it. `@agent` in a message runs the agent whatever the mode. The app writes `chatMode` from the composer's Answer from sheet and from the workspace's Answer from page.
- An agent answer streams `agentThought` chunks (`thought`, such as `@agent: Using SearXNG to search for ...`, or, when the provider is verbose, `` @agent is executing `web-browsing` tool {...} ``, read by `toolCall` as `Running web-browsing`) and `textResponseChunk` pieces that include what it wrote before and between tools. It then sends the whole answer as one `textResponse` chunk with `close: true`, and after it a `finalizeResponseStream` chunk with the `sources`: web results, dozens of them. A chat or query answer has its `sources` on the closing `textResponseChunk`, and its `finalizeResponseStream` has no text. Headers come at once, so the opening `timeout` holds even though the first text takes about 9 s. A query refusal is not stored in the history.
- There is no per-document switch. Switching a file off is `update-embeddings` with `deletes`, and the file is remembered in `Prefs.switchedOff` so Sources keeps listing it. An upload is `document/upload`, then `update-embeddings` with `adds` of each returned `location`. A web page is `document/upload-link` with `link`, and pasted text is `document/raw-text` with `textContent` and `metadata.title`; both answer `documents` as an upload does and are embedded the same way. Their `addToWorkspaces` field is never sent.
- All three take `metadata` with any of `title`, `docAuthor`, `description` and `docSource` (`DocMeta.toJson`, in `core/server_models.dart`), sent only when one is filled in. An upload sends it as a multipart field holding the JSON, which AnythingLLM 1.16.2 reads. Pasted text keeps its author, description and source, but the server stores its title as a file name, so `Meeting notes` comes back as `meeting-notes.txt`. There is no `/v1` call that changes details later.
- `stream-chat` takes `attachments` for one message: each is `name`, `mime` and `contentString`, a base64 data URL. `mime` is `image/*` for a picture and `application/anythingllm-document` for any other file, which the server reads in for that message; the data URL carries the file's own type. A history entry lists `attachments` for images, with the `contentString` it was sent with, but not for documents. `ChatMessage.attachments` keeps each as a `SentFile` (`core/server_models.dart`): its name and, for a picture, the data URL, decoded only the first time `picture` is read, so reading a history for its ids costs no decoding. A sent `Turn` keeps the picture's bytes the same way, and the question shows it small.
- Slash commands are not used. `stream-chat` swaps each server preset for its prompt itself, so one typed is sent as typed, and `/reset` sent as text reaches the model. Clearing a chat (`stream-chat` with `{"reset": true}`) and the preset list (`GET /api/system/slash-command-presets`, which takes the web login) are left alone.
- Developer keys: `GET /api/system/api-keys` answers `apiKeys`, each with `id`, `name` and `secret`, and `POST /api/system/generate-api-key` with `{"name"}` answers `apiKey` and `error`. Both take the web login, so the app does not use them; the toolkit's `pair` does.
- Saved memories and scheduled jobs take the web login, so the app reads them from the toolkit's client API on port 8467, with the developer key: `GET`/`PUT /memory-switches` (`{enabled, learn}`), `GET`/`POST /workspaces/{slug}/memories` (`{memories: {global, workspace}}`, each `id`, `content` and `scope`; a post `{content, scope}`), `PUT /memories/{id}` (`{content}`), `DELETE /memories/{id}`, `POST /memories/{id}/move` (`{workspace}`, null for every workspace), each change answering `memory`, and `GET /jobs` (`{jobs}`, AnythingLLM's own fields, times in UTC). A refusal is `{error}` in the toolkit's words, AnythingLLM's after them (a full list: `Maximum global memory limit (5) reached.`). While memories are off the memory routes answer 403, so `MemoryController` reads the switches first.
- Exchanges: a `/v1` history entry (`convertToChatHistory`) carries `chatId` on both the question and the answer; the closing `finalizeResponseStream` of a chat or query answer carries the new `chatId`, and an agent answer's closing chunk has none (AnythingLLM's `apiChatHandler.js`). Deleting a thread's exchanges (`delete-edited-chats`) and marking an answer (`chat-feedback`) take the web login, so the app does neither: Retry and Edit leave the old exchange on the server.
- `POST /v1/workspace/{slug}/vector-search` with `query` answers `results`, each a passage `text`, a `score` from 0 to 1 and `metadata.title`; with no `topN` or `scoreThreshold` it uses the workspace's own, as an answer does. An empty query is a 400. `GET /v1/system/export-chats?type=` (`jsonl`, `json`, `csv`, `jsonAlpaca`) answers the file itself, not always JSON, so `exportChats` reads the bytes and decodes only a failure. `GET /v1/workspace/{slug}/chats` lists only chats outside any thread and is not used.
- `POST /v1/admin/workspace-chats` with `{"offset": page}` answers `{chats, hasPages}`: every workspace's chats, 20 a page (`ChatLog.pageSize`), newest first, each with `workspace` (`name`, `slug`), `prompt`, `response` (JSON holding `text`, or the text itself), `createdAt` and `user.username`. It answers on a single-user server, though the other `/v1/admin` routes refuse one. `workspaceChats` reads it into a `ChatLog`.
- `"Unknown"` is a server placeholder, read as absent. An upload can answer HTTP 200 with `success: false`; `_decode` fails any answer with `success: false`, whatever its status.
- `GET /v1/workspace/{slug}` also carries `openAiPrompt` and the settings columns in `workspaceSettingSpecs` (type and bounds), and each document's `pinned`. `POST workspace/{slug}/update` takes any of those columns and answers `workspace: null` with a `message` when it refuses.
- A document's `folder/name.json` path is what workspaces use. `GET /v1/document/{name}` takes the file name alone and may leave out `pageContent`.
- `GET /v1/system` gives `settings` with secrets replaced by booleans; a real on-off setting such as `AgentSkillRerankerEnabled` is a boolean too, so a secret is a boolean whose key names a key, secret, token, password or connection string. `POST /v1/system/update-env` writes the `.env` from `KEY_MAPPING`'s names (`systemKeys`, less `AuthToken` and `JWTSecret`, which need the server's force mode). It drops an unknown key or an all-asterisk value without a word, stops at the first failed check with the keys before it already written, and answers `newValues` and `error` with HTTP 200, so `updateSystem` fails on an `error` or on any key sent that is not in `newValues`. Changing `EmbeddingEngine`, `EmbeddingModelPref` or `AzureOpenAiEmbeddingModelPref` makes the server delete every vector (`handleVectorStoreReset`), and changing `VectorDB` deletes the old database's; the app never writes `VectorDB`. `GET /v1/system/vector-count` counts the whole server.
- The closing chunk of an answer, and each history entry, carry `metrics` (`completion_tokens`, `duration`, `outputTps`, `model`, and `inputCost` and `outputCost` when priced; `{}` when unmeasured) and, for an agent, `outputs`: each `{type, payload: {filename, storageFilename, fileSize}}`, `imageGenerationCard` for an image and `PdfFileDownload` and the like for a file. `GET /v1/document/generated-files/{storageFilename}` answers the bytes, an HTML file as `text/html` with `Content-Disposition: attachment`, which `_file` takes where it would refuse the web UI's own page; `generatedFilesOf` keeps only a storage name of letters, digits, `_`, `.` and `-`.
- Embeds: `GET /v1/embed` lists each one's `uuid`, `enabled`, `chat_mode`, `workspace.name` and `chat_count`, but not its allowed sites or limits, so those are set only when it is made. `POST /v1/embed/new` takes `workspace_slug`, `chat_mode`, `allowlist_domains`, `max_chats_per_day` and `max_chats_per_session`, and answers `embed` or an `error`. `POST /v1/embed/{uuid}` changes `enabled` and `chat_mode`; `chat_mode` is only `chat` or `query`. An embed chat's `response` is JSON holding its `text`.

**UI:**

## Conventions

- Dependencies in `pubspec.yaml` are pinned by series (`">=1.6.0 <1.7.0"`). Moving to a newer series is a deliberate edit.
- Doc comments state what a thing is or does, in plain sentences, with `[name]` references. Match that density in new code.
- Every file that is a source of truth for an app or service (its log, `app.json`, its reducer, a playbook) can be viewed raw in the app. Secrets are the exception: the app names them and never shows their value.
- Cache files are never shown. A value derived from them may be, labelled as derived, as long as it can be rebuilt from files the app shows.
